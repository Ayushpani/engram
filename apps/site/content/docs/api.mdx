The REST API is the wire format the TypeScript SDK speaks. Use it directly from any language that can make HTTPS requests — Python, Rust, Go, or a bash script.

## Base URL

- **Sandbox** — `http://localhost:8787` (started with `bun run try`)
- **Hosted** — `https://api.smaran.dev` (coming soon; use self-host in the meantime)

Every request must include an `Authorization: Bearer <api-key>` header. The sandbox accepts `sk_local_dev`; the hosted API uses tenant-scoped keys.

## POST /v1/memories

One-shot save. Runs the full normalizer + self-correction pipeline and commits.

**Request**

```json
{
  "text": "confirm my order — one two three four, actually four three two one",
  "sessionId": "sess_abc",
  "userId": "u_alice",
  "source": "voice",
  "metadata": { "channel": "phone" }
}
```

**Response**

```json
{
  "memories": [
    {
      "id": "mem_01H...",
      "text": "confirm my order four three two one",
      "sessionId": "sess_abc",
      "kind": "fact",
      "validFrom": "2026-08-31T14:30:00Z",
      "validUntil": null,
      "supersedesId": null,
      "confidenceAlpha": 1,
      "confidenceBeta": 1,
      "accessCount": 0,
      "lastAccessedAt": null,
      "createdAt": "2026-08-31T14:30:00Z",
      "updatedAt": "2026-08-31T14:30:00Z"
    }
  ]
}
```

`validUntil: null` means this fact is current. When a later save is
detected as a near-duplicate correction of an existing fact (cross-
session, by embedding similarity), the old row's `validUntil` is closed
out and its id appears as this new row's `supersedesId` — you don't
need to track memory ids yourself for this to work.

`confidenceAlpha`/`confidenceBeta` are a Beta-Binomial belief posterior
(`confidence = alpha / (alpha + beta)`), not a flat scalar — it
strengthens as independent mentions corroborate the same fact across
sessions.

## POST /v1/recall

Recall fuses four channels — vector similarity, keyword full-text,
entity graph, and recency/frequency decay — via reciprocal rank
fusion, then applies each hit's belief confidence as a final score
modulator. Not plain vector search.

**Request**

```json
{
  "query": "what did the caller confirm",
  "sessionId": "sess_abc",
  "topK": 5,
  "includeCrossSession": false,
  "asOf": "2026-08-15T00:00:00Z"
}
```

`asOf` is optional — point-in-time recall. Omit it for "current facts
only" (the default). Pass a past timestamp to see what was true as of
that instant, even if it's since been corrected.

**Response**

```json
{
  "hits": [
    {
      "memory": {
        "id": "mem_01H...",
        "text": "confirm my order four three two one",
        "sessionId": "sess_abc",
        "kind": "fact",
        "createdAt": "2026-08-31T14:30:00Z"
      },
      "score": 0.91,
      "tier": "session",
      "channels": { "dense": 1, "keyword": 2, "temporal": 1 }
    }
  ],
  "latencyMs": { "total": 2, "embed": 1, "search": 1, "rerank": 0 }
}
```

`channels` shows the rank this hit held in each retrieval channel
before fusion — absent for a channel means the hit didn't surface
there at all. Useful for debugging why something did or didn't recall.

## POST /v1/ingest/partial

Streaming ingestion during a live voice turn. Overwrites the working buffer.

```json
{ "sessionId": "sess_abc", "text": "confirm my order — one two three four" }
```

Returns `204 No Content`. Call as often as the ASR ships partials.

## POST /v1/ingest/commit

Freezes the buffer, runs self-correction, writes to storage. Exactly once per turn.

```json
{ "sessionId": "sess_abc", "userId": "u_alice", "source": "voice" }
```

Response is the same shape as `POST /v1/memories`.

## GET /v1/profile

Fetch the standing per-user profile — a consolidated summary folded
from recurring facts across all of a user's sessions, so a voice agent
can pull stable context at call start with one point-lookup instead of
a fresh recall. Postgres-backed deployments only (not sandbox mode).

```
GET /v1/profile?userId=u_alice
```

**Response**

```json
{
  "summary": "Lives in Powai, Trikutta Towers. Phone ends 913.",
  "confidence": 0.83,
  "sourceMemoryIds": ["mem_01H...", "mem_01J..."],
  "updatedAt": "2026-08-31T09:00:00Z"
}
```

`404` if no profile has been consolidated for this user yet.

## POST /v1/profile/consolidate

Recomputes the profile from the user's current (non-superseded)
memories: clusters them by embedding similarity, keeps clusters with
2+ corroborating memories, and folds each into one summary line.
Confidence is Beta-Binomial — more corroborating mentions means a
tighter, more confident posterior, not a bigger number from a single
model guess. No cron trigger yet; call this on whatever cadence suits
your deployment.

```
POST /v1/profile/consolidate?userId=u_alice
```

**Response**

```json
{
  "consolidated": true,
  "summary": "Lives in Powai, Trikutta Towers. Phone ends 913.",
  "confidence": 0.83,
  "sourceMemoryIds": ["mem_01H...", "mem_01J..."]
}
```

`{ "consolidated": false, "reason": "not enough recurring evidence" }`
if no cluster had 2+ corroborating memories yet.

## Error codes

| Status | Meaning |
|---|---|
| `401` | Missing or invalid `Authorization` header |
| `403` | Key doesn't belong to the tenant that owns this session |
| `422` | Body failed schema validation (Zod error is included in `detail`) |
| `429` | Rate limited — check `Retry-After` |
| `500` | Server error — please report at github.com/Ayushpani/smaran/issues |

<Callout tone="info" title="Idempotency">
Include an `Idempotency-Key` header on `/v1/memories` if you're retrying at the network layer — Smaran will collapse duplicate writes for 24 hours.
</Callout>
